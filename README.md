# stdq — 中国建筑规范条文级检索

把**中国建筑规范 Markdown** 建成条文级可检索库：jieba 分词 + LIKE 召回 + 章节标题扩展词 + BM25 词级融合 + bge 语义排序。
输出带**条文号、强条标记、条文说明**，供人查、也便于接给 LLM 当检索层。

> 仓库内 `examples/sample-standards/` 是三本**完全虚构**的示例规范，用来演示流程；不含任何真实规范原文。

## 它解决什么

### 查询侧

| 直接问 LLM | 用 stdq |
|---|---|
| 规范原文几十万字塞不进上下文 | 只把命中的那几条条文取出来 |
| "疏散距离"、"卷材防水层"这类专业词，关键词搜不到 | 同义词表 + 章节标题扩展词 + 语义兜底一起召回 |
| 不知道条文号、不知道哪条是强条 | 结果直接带 `§4.1.3`、`🔴强条`、`📖有说明` |
| 条文说明和正文混在一起 | 正文/说明分开存，可分别取用 |

### 入库侧（这类应用真正的难点）

查询环节方案已经成熟（向量库、全文索引、RAG 框架都能做）。**真正花时间的是把中文规范变成可检索、可信、结构化的条文库**——转换质量决定检索质量，入库错了，检索再强也搜不到。

| 常见做法 | 用 stdq |
|---|---|
| 转换稿抽到多少算多少 | **先鉴别质量、再入库**：条文号粘连检测、MD 与库逐条对账、OCR 字符体检当硬闸门、跳号自动分类（只挑"真漏抽"动手） |
| 只存条文正文 | **按结构拆开存**：条文 / 条文说明 / 表格 / 术语 / 附录各自成表，说明能与正文分开取用 |
| 分不清哪条必须执行 | **区分强条与"严格"条文**（按公告句式认定，不靠"必须 / 严禁"这类词猜） |
| 不知道一本规范属于哪一类 | **双重分类**：建筑类型（住宅 / 公建 / 工业 / 通用，可据此过滤检索）+ 专业主题（13 类，参与检索加权） |
| 清单靠手工维护 | **在库清单自动生成**：每次建库重写，条数 / 强条数 / 专业主题一览 |
| 新旧版本混在一起 | **废止关系可查**：新版公告里的废止声明自动解析入库，整本被替代的旧版默认不再召回 |

每一类问题的**识别方法、判定判据与修复工具**见 [`docs/ingest-sop.md`](docs/ingest-sop.md) 与 [`stdq/tools/README.md`](stdq/tools/README.md)。

## 快速开始

```bash
pip install -e ".[embed]"              # 基础 + 语义依赖（只要关键词检索：pip install -e .）

export STDQ_DATA_DIR=~/.stdq
mkdir -p "$STDQ_DATA_DIR/standards"
cp examples/sample-standards/*.md "$STDQ_DATA_DIR/standards/"

stdq rebuild                           # 建库：扫 MD → 解析 → 入库
stdq embed-build                       # 生成条文向量
stdq daemon start -d                   # 起常驻进程 ← 需要它，理由见下一节

stdq list                              # 看库里有哪些规范
stdq search "疏散安全出口"              # 查
stdq clause SAMPLE-10001-2026 3.1.1    # 取某条原文（含条文说明）
stdq strong SAMPLE-10001-2026          # 只看强条
```

## 常驻进程（需要起）

检索要用语义模型（约 1 GB）。这项安装**需要起一个常驻进程**：模型只加载一次，之后每次查询直接算。

不起它也能查，但每次查询都要**现场重新加载一遍模型**，速度差很多很多：

| 单次查询 | 耗时（96 条的小样例库实测） |
|---|---|
| 不起常驻进程 | **13.3 秒**（每次重新加载模型） |
| 起了常驻进程 | **0.15 秒** |

（首次加载模型会到分钟级，取决于机器；上表是模型已在系统缓存后的数字。）

也就是说，不常驻的代价不在"能不能用"，而在**每次查询都要等**——库越大、查得越频繁，越难忍受。要"敲下命令就出结果"，就得有常驻进程。

```bash
stdq daemon start -d         # 起（模型只加载一次）
stdq daemon status           # pid / ready / socket 三态
stdq daemon stop
```

要开机自启就用 `deploy/stdq-daemon.service`（systemd 模板，里面标了要改哪几处）。

> **检索质量与起不起常驻无关**：召回与排序逻辑都在库层（`stdq/search.py`），两条路走的是同一个函数、结果一致。常驻解决的是**速度**——但速度差很多很多（见上表）。

## 依赖分级

| 装了什么 | 能用到什么 |
|---|---|
| 只装 `jieba` | LIKE 召回 + 词级排序（可用） |
| 再装 `numpy` | 语义兜底召回、章节命中加权 |
| 再装 `sentence-transformers` 并跑过 `embed-build` | 完整：bge 余弦排序 + 章节标题扩展词 + BM25 融合 |

缺哪一层只是**能力弱一点，不会不能用**——缺依赖时会在 stderr 说一句然后降级，不报错退出。

## 出问题时

`tools/` 下是入库前后用的质检与修复脚本（对账、条文号连续性、OCR 字符体检、各类 MD 修复）。**转换质量决定检索质量**，拿到一批转换稿建议按 `tools/README.md` 里的顺序过一遍。

## 建自己的库（用你手上的规范）

1. **准备 Markdown**：每本规范一个 `.md`。文件名建议 `规范号 规范名称.md`（如 `GB 5xxxx-20xx 某某规范名称.md`），程序据此提取规范号与名称。
2. **条文格式**：`X.Y.Z` 形式的条文号开头，正文跟在后面；条文说明单独成节（`条文说明`），程序会与正文分表关联。
3. **入库**：

```bash
stdq rebuild        # 建库（幂等，可反复跑）
stdq profession set <规范号> <主题>    # 标专业主题（结构/给排水/暖通/电气/节能…）
stdq embed-build    # 语义检索就绪（可选，但推荐）
```

4. **自查**：

```bash
stdq list           # 条数是否合理
stdq info <规范号>  # 单本详情
stdq abolished      # 废止条文（老规范被新版替代的）
```

**转换质量决定检索质量**。若你的 MD 来自 PDF 转换，建议先检查：条文号是否连续、有没有被表格切断、章节标题是否被误当条文。见下面「出问题时」一节。

## 命令一览

| 命令 | 作用 |
|---|---|
| `rebuild` | 建库（扫 `$STDQ_DATA_DIR/standards/*.md`） |
| `list` / `info <号>` | 在库清单 / 单本详情 |
| `search <词>` | 检索（默认走常驻进程，没有就本地算） |
| `clause <号> <条文号>` | 取条文原文（`--no-note` 去说明） |
| `strong [号]` | 强条清单 |
| `term <号> [关键词]` | 术语查询 |
| `appendix <号>` | 附录条目 |
| `catalog` | 重新生成在库清单 |
| `term <号> <术语>` | 术语查询 |
| `appendix <号>` | 附录 |
| `catalog` | 生成在库清单 Markdown |
| `abolished` | 废止条文 |
| `profession set/list` | 专业主题标注 |
| `embed-build` | 生成条文向量 |
| `daemon start/stop/status` | 常驻进程（推荐） |

## 常见问题

**Q：可以不起常驻进程吗？**
可以，但每次查询都要现场加载语义模型，**速度差很多很多**（实测 13.3 秒 vs 0.15 秒）。日常使用的话，常驻进程是标准配置——装完就起它。

**Q：语义依赖装不上 / 装完跑不动？**
不装也能查——LIKE 召回 + BM25 排序照常工作，只是没有语义排序和章节加权。

**Q：我可以把规范原文放进这个仓库吗？**
别。规范文本有著作权，本仓库只提供**引擎**与**虚构样例**。你自己的规范放在自己的数据目录里。

**Q：换了机器，库要重建吗？**
要重新 `rebuild`（SQLite 单文件可直接拷，但向量文件与解释器/模型版本相关，建议重建后重新 `embed-build`）。
