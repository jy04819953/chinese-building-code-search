# 架构

## 分层

```
Markdown 规范
   │
   ▼   parser/          解析：把 MD 切成条文 / 说明 / 章节 / 附录 / 术语
   ▼   db.py            入库：SQLite 单文件 + FTS 全文索引 + 章节目录
   ▼   search.py        检索：召回 → 排序（全部质量逻辑在这里）
   ▼   cli.py           命令：stdq <子命令>
   ▼   daemon.py        常驻：只是让模型留在内存里（可选）
```

`tools/` 不在查询路径上，是入库前后按需跑的质检与修复脚本。

## 模块

| 模块 | 职责 |
|---|---|
| `consts.py` | 常量与路径（数据目录、库路径、socket、正则、检索参数默认值） |
| `parser/common.py` | 共用工具（正文起点、文档尾部识别、字符归一） |
| `parser/clauses.py` | 条文抽取（编号 + 正文，含粘连兜底） |
| `parser/notes.py` | 条文说明抽取（与正文分表关联） |
| `parser/toc.py` | 目次抽取（章 / 节 / 附录 → `clause_chapters`） |
| `parser/meta.py` | 元数据（规范代号、名称、公告里的强条清单、废止声明） |
| `parser/tables.py` | 表格处理（HTML 表格识别与保留） |
| `parser/term.py` | 术语标准抽取（与常规规范不同的提取路径） |
| `parser/appendix.py` | 附录抽取与区间识别 |
| `db.py` | 建库：扫描 MD → 调解析器 → 写库 → 重建 FTS；幂等 |
| `catalog.py` | 在库清单（`catalog.md`）+ 建筑类型映射读取 |
| `search.py` | 召回与排序（章节扩展词 / 章节加权 / BM25 融合 / 语义兜底） |
| `cli.py` | 命令行子命令与输出渲染 |
| `daemon.py` | 常驻进程：Unix socket 服务 + 模型常驻 + 标准 daemonize |

## 数据流（一次查询）

1. `cli.py` 收到 `search` → 先试常驻进程（`search_via_daemon`）
2. 常驻进程在跑 → 它收到请求后调用**同一个** `search()`；没跑 → CLI 本地直接调 `search()`
3. `search()` 按 §「检索是怎么排出来的」的七步召回与排序
4. 返回结果元组 `(规范号, 条文号, 正文, 有无说明, 说明, 强条, 严格)` → `cli.py` 渲染

**关键点**：质量逻辑只有一份、在 `search.py` 里。daemon 与 CLI 走的是同一个函数，所以**起不起常驻进程，结果完全一致**，区别只有速度（模型是否常驻）。

## 几个设计决定

| 决定 | 原因 |
|---|---|
| **SQLite 单文件** | 库可整体拷贝、可 `sqlite3` 直查排障；规范库规模（数万条）远未到需要服务端数据库 |
| **条文正文与说明分列存** | "说明该不该显示"是查询期决定，混在一起就没法分层输出 |
| **章节目录单独成表** | 章节标题扩展词与章节加权都要按节关联，靠正文串匹配不可靠 |
| **daemon 只负责常驻** | 让它同时承担排序质量，会让"不起 daemon 就拿到降级结果"变成隐式行为——所以质量逻辑放在库里 |
| **依赖分级** | 缺 numpy / 模型时降级而非报错退出：关键词 + BM25 一条路始终可用 |
| **解析器和工具同仓** | 入库质量直接决定检索质量，两者分开维护必然漂移 |

## 配套工具（`tools/`）

22 个脚本，按用途分六组（入库前排查 / 入库后对账体检 / MD 修复 / 附录补库 / 转换后处理 / 修复影响面复核）。清单与用法见 [`../stdq/tools/README.md`](../stdq/tools/README.md)。
