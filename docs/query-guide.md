# 查询手册

README 让你跑起来；这份手册让你**用顺、用到不出错**。三件事：怎么查、结果为什么这么排、哪里最容易出错。

---

## 1. 命令速查

| 操作 | 命令 |
|---|---|
| 规范搜索 | `stdq search "关键词"` |
| 限定单本规范 | `stdq search "关键词" --std GB-50016-2014` |
| 限定建筑类型 | `stdq search "关键词" --type 住宅` |
| 取某条原文 | `stdq clause GB-55038-2025 4.2.2` |
| 取原文但不要说明 | `stdq clause GB-55038-2025 4.2.2 --no-note` |
| 强条清单 | `stdq strong GB-50763-2012` |
| 术语查询 | `stdq term GB-55038-2025 住宅` |
| 附录 | `stdq appendix GB-50016-2014` |
| 在库清单 | `stdq list` / 单本详情 `stdq info GB-55038-2025` |
| 检索不到时的定位 | `python -m stdq.tools.verify_md_vs_db`（对账）· `python -m stdq.tools.stdq_check`（条文号连续性） |
| 建库 / 重建 | `stdq rebuild` |
| 生成向量 | `stdq embed-build` |
| 标专业主题 | `stdq profession set GB-50016-2014 fire` / 看分布 `stdq profession list` |
| 常驻进程 | `stdq daemon start -d` / `status` / `stop` |
| 废止条文 | `stdq abolished <规范代号>` |

**表格输出风格**：`--table-style {markdown|compact|raw}`（默认 `markdown`；`clause` 命令不支持）。`--limit` 默认 30。

**规范号入参格式**（踩坑高发）：库里 `std_code` 存的是 `GB-50016-2014` 这种**字母 + 连字符 + 数字**形式。`GB50016-2014` 会被自动补连字符，但**带空格的 `GB 50016-2014` 会原样保留** → 后续匹配不上 → 报"未找到条文"。**统一用 `GB-50016-2014` 或 `GB50016-2014`**，不要写空格。

## 2. 数据是怎么组织的

```
$STDQ_DATA_DIR/
├── standards/            放你的规范 Markdown（一本一个 .md；根目录下平铺也认）
├── standards.db          索引（SQLite，单文件）
├── embeddings/           ids.npy + embeddings.npy（条文向量）
├── synonyms.txt          同义词表（外部数据，可选）
├── catalog.md            rebuild 自动生成的在库清单
└── stdq_daemon.*         常驻进程的 pid / ready / socket / 日志
```

`standards.db` 里：

| 表 | 内容 |
|---|---|
| `standards` | 规范元数据（代号、名称、条数、强条数、专业主题） |
| `clauses` | 条文（正文 + 该条的说明 + 强条/严格标记） |
| `clause_chapters` | 章节目录（章 X / 节 X.Y / 附录），**章节扩展词与章节加权的数据源** |
| `abolished` | 废止关系（`abolish_type` = `whole` 整本废止 / `clauses` 逐条覆盖） |
| `clauses_fts` | 全文索引 |

> 条文正文与条文说明**分列存**、章节目录**单独成表**——不是设计洁癖，是因为"说明该不该显示"、"某条属于哪一节"这两件事在查询时各自要用。

## 3. 查询工作流（七步，别跳）

0. **先判断建筑类型与适用范围**：住宅 / 公建 / 工业 / 通用。引用条文前确认该规范适用范围（例如"商业服务网点"≠ 某些规范里的"商店建筑"）。
1. **看在库清单**：`grep -i "关键词" $STDQ_DATA_DIR/catalog.md`。不在库就直接说"不在库、缺哪本"，不要绕去召回擦边条文。
   - ⚠️ `catalog.md` 的分类是**建筑类型**（住宅/通用/公建/工业），不覆盖专业维度。问"电专业有什么规范"要看 `standards.profession` 列（13 个主题：`structure / plumbing / hvac / electrical / barrier_free / energy / gas / curtain_wall / fire / civil_defense / waterproof / roof / general`）——`stdq profession list` 只给计数，要规范名得直查库。
2. **有没有现成答案**（自己攒的速查表 / 笔记）。
3. **搜索**：`stdq search "关键词"`。召回链路见 §4。
4. **grep 本地 MD 补充**：数据目录里没入库的参考文件（笔记、摘录）stdq 搜不到，`grep` 能搜到。
5. **读原文确认**：`stdq clause <code> <条文号>` 或直接看 MD。
6. **下结论 / 横向对比**：多本规范涉及时做对比表。

### 搜索次数上限

| 类型 | 上限 | 停止条件 |
|---|---|---|
| **查询类**（"X 是多少 / 有什么要求"） | 2–3 次 | 已经能回答就停，不反复换词 |
| **分析类**（多规范冲突 / 方案比选） | 最多 6 次（两轮各 3 次） | 第一轮广搜定位，第二轮验证前提 |

**出答案前自检**：召回的条文够回答吗？够 → 直接出，停。不够 → 才进兜底（`--type` / `--std` 缩小 → 换正规用词 → SQL 直查）。

**检索词就按你想到的写**：口语词（"地下车库行人门高度"）往往第一条 `LIKE '%行人门%'` 就是终局——不必先绕去同义词扩展、范围限定这条路。

## 4. 检索是怎么排出来的

一条查询经历这些步骤（都在 `stdq/search.py` 的 `do_search` 里，**起不起常驻进程走的是同一套逻辑、结果一致**；但强烈建议起常驻——不起的话每次查询要现场加载模型，实测 13.3 秒 vs 0.15 秒）：

| 步骤 | 做什么 | 解决什么问题 |
|---|---|---|
| 1. jieba 分词 + LIKE 召回 | 拆词后在候选池里匹配（每路 5000 条上限） | 基础召回 |
| 2. 同义词表组内互扩 | `synonyms.txt` 里同组词互相加入召回词集（**组内扩、组间隔离**） | 词面盲区（"强电间"→"变电所"） |
| 3. 章节标题扩展词 | bge 召回 top 10 章节标题，整段送进 LIKE | jieba 不懂建筑术语（拆出"做法"这种废词时，扩展词充当专业词表） |
| 4. embedding 余弦排序 | bge 向量算相似度 | 语义排序 |
| 5. 章节命中加权 | 条文所属章节标题命中查询词 → `sims` 加分（完整查询 +0.3，拆词命中 +0.25 / +0.15，每条只加一次取最高） | 主题相关的子条文不被语义分压死 |
| 6. BM25 词级融合 | `final = sims + 0.30 × bm25_norm`（归一化到 0–1） | 补纯语义对**数字 / 编号 / 罕见术语**不敏感（"疏散距离 25m" vs 30m） |
| 7. 单本规范上限 | 每本规范最多 8 条 | 防单本霸屏 |

**调参的位置**：`CHAPTER_TITLE_TOPN`（默认 10）、`_BM25_BETA`（默认 0.30）、`PER_CAP`（默认 8），都在 `stdq/search.py` 顶部或函数内常量。

**改排序参数前**：先攒 30–50 个真实查询用例跑基线，改完用**同一批**对比。凭印象"这样应该更准"不算数。

**同义词表**：加词要谨慎——有歧义的组合（"屋顶 / 屋盖"这类）进了表会污染候选池；组内互扩、组间不要混。

## 5. 输出规范

### 三段式（查询类问题）

```
【条文展示】  →  【数据汇总】  →  【精简结论】
```

- **条文展示**：每条原文一字不动，关键数值加粗（如 **0.80m**）；分条款展示，**依次排列、不加"主依据 / 放宽 / 关联"这类主次标签**（查询人自己判断）。
- **数据汇总**：表格，列含规范来源。
- **精简结论**：1–2 句。

### 引用格式

**规范全称带《》**，且**每一个出现位置都要带**：

- ✅《住宅项目规范》GB 55038-2025 §4.2.2
- ❌ GB 55038-2025 §4.2.2（缺《》）
- ❌ 只有条文展示块带了《》，而**数据汇总表格的"来源"列**和**精简结论**里只写标准号

出答案前扫四个位置：① 条文展示块每条标题 ② 数据汇总表格"来源"列 ③ 精简结论里再次点名的规范 ④ 行文中夹带的"按 X 规范要求"。

**条文标题行整行加粗**：`**《规范全称》GB XXXXX-XXXX §X.X.X（标记）**`——规范全称 + 条款号 + 标记**一起**包进 `**`。条文正文行、`📝` 说明行、表格内文字**不**加粗。

### 标记的含义（重要：只代表该条）

| 标记 | 含义 | 常见的错误推断 |
|---|---|---|
| 🔴 强条 | **这一条**是强制性条文 | ≠ 这本规范所有条都是强条 |
| ⚠️ 严格 | 该条标记为"严格"类条文 | — |
| 📖 有说明 | 该条**有**条文说明 | ≠ 这本规范所有条都有说明 |
| 🚫 已废止 by X | **这一条**被 X 覆盖 | ≠ 这本规范整本被废止 |

**"从单条标记推断整本属性"是脑补**。要判整本状态就查库：

```sql
SELECT source_std, target_std, abolish_type, clause_nos FROM abolished WHERE source_std = 'GB-50016-2014';
SELECT clause_count, strong_count FROM standards WHERE code = 'GB-50016-2014';
```

措辞规范：

- `abolish_type='whole'` 且替代新规在库 → 「《GB XXXX-XXXX》整本废止，替代规范《GB XXXX-XXXX》已在库」（旧版条文默认不再召回）
- `abolish_type='whole'` 但新规不在库 → 「整本废止，新规未入库，旧版条文照常召回」
- `abolish_type='clauses'` → 「《GB XXXX-XXXX》§X.X.X 被《GB XXXX-XXXX》§X.X.X 废止，其余条文仍现行」——**绝不用"整本废止"措辞**

**已废止条文照样展示完整原文**，在原文后附一句废止说明，不要压缩成要点。

### 正文与条文说明分层

条文正文在前，说明用 `📝` 标出、单独成行，不混成一段。

### 纯文本客户端的排版

有些客户端按字面投递文本、不渲染 Markdown，**连续两个 `---` / 多空行会被吞掉**，导致标题、表格、结论各断一处。给这类出口写答案时：

- 每条条文独占段落，**标题行 / 正文行 / `📝` 说明行各占一行**（空行隔开）；条文之间**不用 `---` 分隔**
- `**【数据汇总】**` 标题紧接表格，中间不空行
- `**【精简结论】**` 收尾用一整段，不分段、不接下一段

## 6. 硬规则（踩坑清单）

这些是实际吃过亏才立的，逐条都有代价。

**数字与原文**

1. **数字只能来自原文**。禁止凭印象推算条数、耗时、参数；要说得先查库、看文件时间戳。
2. **禁止用"工程惯例"补位**。召回为空或条文只讲原则时，**不要编造数值**——去查同主题的专门规范，或直接说没有依据。
3. **OCR 残缺表格禁止外推**。库里的表格可能是残缺的：
   - 迹象：`<table><table>` 空标签、`3.05.07.08.0` 这种数字粘连、一行里 3+ 个浮点数
   - **禁止**按"递增规律 / 工程惯例"补全再当结论展示
   - 正确做法：① 明说"库原文残缺 N 行，需对照 PDF" ② 只展示能确认的部分 ③ 走 §8 的表格修复
   - 反面：一张 12 行的表 OCR 只留 4 个数，按"递增"补满 12 行——原表是按视觉相邻分组，补出来的 11 行全错
4. **单条标记 ≠ 整本属性**（见 §5）。

**流程纪律**

5. **动数据前先备份**：改 MD 前 `cp x.md x.md.bak`；改动后 `SELECT COUNT(*) FROM clauses` 对比，**条数下降 >10% 立即回滚**（`rebuild` 也会自动在 `backups/` 留一份）。
6. **`rebuild` 之后不要擅自跑 `embed-build`**：它要给每条条文算向量，耗时按机器差别很大（强机器几十分钟量级）。跑之前先确认。
7. **长任务期间 MD 与库只读**：`embed-build` 跑着的时候不要 `rebuild`、不要改 MD——库和向量会对不齐，白跑一次。新发现的问题先记到文本文件，等它跑完再处理。
8. **改代码 / 换依赖后重启常驻进程**：常驻进程启动时 import 一次代码、加载一次模型，运行中不会自动重载。改完不重启，你以为在跑新代码，其实还是旧的。
9. **`rebuild` 后向量会过期**：库里的条数和向量条数不一致时，`rebuild` 会提示；此时语义排序只覆盖旧条文，重新 `embed-build` 才一致。

**代码与调试**

10. **改了"看起来生效"不等于生效**：改完**必须真跑一次命令验证**（尤其批量替换：可能只改了第一处、或踩了 Python 元组 rebind 这种坑）。
11. **`(a,b) IN ((x,y),...)` 在 SQLite 上兼容性差**，返回 0 行**不报错**——用 OR 链代替。
12. **结果元组加字段后**，`r[7]` 这类**位置索引会取到旧字段**，用 `r[-1]` 或明确位置。
13. **新功能要同步三处**：代码、库 schema、文档（用法与踩坑）。缺一样就会出现"文档和代码不一致"。

**正则与长字符串**

14. 入库用的正则函数**必须拿真实的大 MD 文件跑一遍**（几百 KB 级别）并加超时——单测通过不代表真数据不卡死。

## 7. 故障排查

**搜索没结果**

1. 这条路它本来就没有 → `grep -i "关键词" $STDQ_DATA_DIR/catalog.md` 看规范在不在库
2. 换词：口语词 → 规范里的正规用词；或用 `--std` / `--type` 缩小范围
3. 终极兜底（直查库）：

   ```bash
   python3 -c "
   import sqlite3, os
   db = os.path.join(os.environ['STDQ_DATA_DIR'], 'standards.db')
   for r in sqlite3.connect(db).execute(\"SELECT std_code, clause_no, substr(content,1,80) FROM clauses WHERE content LIKE '%关键词%' LIMIT 20\"):
       print(r)"
   ```
   （装了 `sqlite3` 命令行的话，也可直接 `sqlite3 \"$STDQ_DATA_DIR/standards.db\" \"…\"`。）

4. 还是空 → 跑对账：`python -m stdq.tools.verify_md_vs_db`（看 MD 里有、库里没有的条文）

**常驻进程像在跑、但查询很慢或报错**

按顺序验证三件事：

```bash
stdq daemon status                                   # pid / ready / socket 三态
```

- 三态任一不对 → `stdq daemon stop && stdq daemon start -d`，等 `ready` 文件出现（首次要加载模型）再查
- 都正常但查询还是慢 → 大概率是**向量文件过期或缺失**，语义排序退回关键词路径；`stdq embed-build` 后重启

**结果显示的顺序明显不合理**

按顺序查：

1. `clause_chapters` 表是不是空的？章节扩展词和章节加权全靠它。为 0 说明建库时没抽到章节目录（MD 里没有目次段时会发生）。
2. 向量文件是不是过期？（`rebuild` 会提示条数不一致）
3. 再考虑调参（§4），且**先攒用例跑基线**。

**"库里没有"但 MD 里明明有**

跑 `python -m stdq.tools.verify_md_vs_db` 对账，它会逐条比出「MD 有库无 / 库有 MD 无」。常见原因：条号和上一句粘在一行、被表格吞掉、章节标题被当条文。对应修复脚本见 `tools/README.md`。

## 8. 表格与排版失真

转换出来的 MD 会有几类共性问题：条文号粘在上一句末尾、条文被拆成多行、表格被吞、下一章标题粘进上一条、尾部整块（用词说明 / 引用标准名录）粘进条文。

**处理原则：先预演、看清差异、再写盘。**

```bash
python -m stdq.tools.verify_md_vs_db              # 先看差在哪
python -m stdq.tools.fix_table_swallow            # 默认只报告，不写盘
python -m stdq.tools.fix_table_swallow --apply    # 确认差异无误才写盘（自动备份）
```

**定向修单条（不 rebuild）**：库里只有个别条文的表格残缺时，可以直接 `UPDATE` 那条 content + 重建 FTS，比整库重来快得多。收尾清单：

1. 改前备份库文件
2. `UPDATE clauses SET content=? WHERE id=?`
3. `INSERT INTO clauses_fts(clauses_fts) VALUES('rebuild')`
4. 重新 `stdq search` 验证该条能召回
5. 若该条有向量，用 `python -m stdq.tools.embed_patch` 定点刷新（不必全量 `embed-build`）

**同类失真铺开到多本时**：不要一条条改，写批量脚本 + 先 dry-run 全库扫描、输出影响面清单，确认后再统一写盘。

## 9. 库外场景：近期规范动态

`stdq search` 只查本地库。"最近发布了哪些规范""这本有新版吗"这类问题超出库范围，需要外部来源：

1. **库内先查**：`grep <code> $STDQ_DATA_DIR/catalog.md`，看是否在库、`updated_at` 是否是近期
2. **外部官方源优先**：主管部门公告 / 国家标准全文公开系统；转载站点作辅助
3. **编制计划类**：年度编制计划常见为 xlsx 附件，用标准库 `zipfile` + `xml.etree` 解析即可（不一定需要 openpyxl）

输出时只筛与你工作直接相关的几本 + 标注有没有新增强条，不要把整份计划展开。
