# 入库手册：从 PDF 到可检索条文库

查询侧的操作手册见 [`query-guide.md`](query-guide.md)；这份讲**怎么把你手上的规范变成可检索库**。

> 文中出现的规范编号只是示例。路径一律用 `$STDQ_DATA_DIR`。
> 命令统一两种写法：引擎命令 `stdq xxx`，配套脚本 `python -m stdq.tools.xxx`。

---

## 0. 入口判断：常规规范还是术语标准

| 类型 | 判定 | 走哪条 |
|---|---|---|
| 常规规范 | 文件名不含"术语标准 / 词汇" | §1 |
| **术语标准** | 文件名含"术语标准"或"词汇"（如 GB/T 50504、GB/T 5907 系列） | §3 |

**判定看文件名，不要看内容。** 普通规范里也有术语章，其格式是术语标准的**子集**——按内容判会把普通规范误判成术语标准（实测某本被误判后条数从 480 掉到 23）。解析器内部也是先看文件名，内容判定只作无文件名时的兜底。

---

## 1. 常规规范入库（逐项打勾，不凭记忆挑着做）

> 经验：一次同日入库两本，**漏了 4 步**（粘连检测 / 断句修复 / 主题标注 / 图片），其中图片那步让 18 处引用全部悬空，而条文解析完全正常——**看不出问题**。
> 做法：开工前抄成清单，每步记下**实测证据**（命令输出、条数），有一步空白就不收工。

### 步 0：入库前基线（先做这三件，再动 MD）

① **体检源文件**：页数、有无书签、每页文字量（判文字型还是扫描件）、条文号能否提取 → 决定用哪个转换器、要不要强制 OCR。
② **核实现行状态**：这本书现在还有效吗、有没有被替代？**别把已废止的书当新版入库**。（步 9 的废止核对只管"新版公告里声明废止旧版"这一种情形。）
③ **确认命名**：见步 1，命名表先给使用你的人确认（名字错 = 清单对不上）。

### 步 1：MD 命名

文件名统一为 `标准号 中文全称.md`（例：`GB 50033-2013 建筑采光设计标准.md`）。

- 标准号内用**空格**；`GB/T` 写成 `GB-T`、`JGJ/T` 写成 `JGJ-T`（`GB-T 51313-2018 ×××.md`）
- 库里的 `std_code` 用**连字符**形式（`GB-50033-2013` / `GB-T-51313-2018`），与文件名联动
- ⚠️ **文件名里含 `19xx` / `20xx` 的段会被当作年份截断**：`SAMPLE-T-20001-2026` 会被解析成 `SAMPLE-T-2000`。命名时避开这种冲突段。

### 步 2：放进数据目录

放到 `$STDQ_DATA_DIR/standards/`（根目录平铺也认）。替换旧文件前先 `cp xxx.md xxx.md.bak`。

⚠️ **非规范文件不要放在会被扫描的目录顶层**（体检报告、待办清单、扫描清单这类自用笔记）。`rebuild` 会把 `standards/*.md` 全部收录，**哪怕解析出 0 条条文也会进库和清单**，变成一条"假规范"。要留在本地就放**子目录**（默认不递归扫描）。

已误收的三步清理：① 移到子目录 ② `DELETE FROM standards WHERE code='<误收代号>'` ③ 重跑 `rebuild`（它会按库重写清单）。

### 步 3：图片

若 MD 引用了图（`![](images/…)`），把图放到 `$STDQ_DATA_DIR/standards/images/<规范名>/`，引用写成**相对路径** `images/<规范名>/<hash>.<ext>`。

- ⚠️ **转换器新产物的扩展名可能与旧目录不同**（旧图 `.png`、新转换 `.jpg`）→ 同名不同扩展名，**引用全部悬空，而条文解析看不出问题**
- ⚠️ **两种引用形式都要改**：Markdown 的 `](…)` 和 HTML 的 `<img src="…">`（表格内嵌图最容易漏）
- **悬空检查**：

  ```bash
  grep -oP 'images/[a-f0-9]+\.(jpg|png)' 规范.md | sort -u | wc -l   # 引用数
  ls "$STDQ_DATA_DIR/standards/images/<规范名>/" | wc -l             # 实际文件数
  ```

  引用数 > 文件数 = 悬空，要补。反向（文件远多于引用）**属正常**——转换器会输出很多表格截图/误识别图，只要"引用的都有文件"即可。
- **图源**：转换器输出目录里的图片文件夹是唯一图源，**别急着清**。

### 步 4：粘连检测

```bash
python -m stdq.tools.detect_clause_drop "$STDQ_DATA_DIR/standards/<你的.md>"
```

**必须传路径**——不传参数只打印用法、不报错也不检测。输出 `✅ 无粘连` 才算过。

它只覆盖**已知的几类写法**，抓不到"条文号后跟数字正文"那种（见 §4）。所以：

### 步 4b：OCR 字符体检（硬闸门）

```bash
python -m stdq.tools.scan_ocr_anomalies                       # 扫库内文本
python -m stdq.tools.scan_ocr_anomalies "<MD 全路径>"          # 扫 MD
```

退出码 0 = 通过（可有告警）；1 = 有硬失败，**闸门没过**。三个硬门：

| 硬门 | 说明 |
|---|---|
| 日文假名 | 中文规范里出现平/片假名没有正当理由，混一个就是 OCR 认错了形近字（`エ`→工、`の`→、；`へ`→（ 等）。脏字符会落进条文正文**和**章节标题，后者参与章节加权 |
| 表号被拆行 | MD 写成「…应符合表」+ 下一行 `5.4.1的规定。` → 解析器把续行当新条文开头，**紧随的整张表连同该条正文尾部一起不入库** |
| 条号粘在行尾 | MD 写成「…宜设置纵向受拉钢筋。10.3.9厂房柱间支撑…」→ 解析器只认**行首**条号 → **该条整条不进库** |

覆盖范围：MD 与库内 `clauses.content`、`clauses.note`、`clause_chapters.title` **四处都扫**——最后那个最容易漏。

**只提示不拦的**（人判断后按多数写法归一）：同一格多种写法、表格数字断裂（`1,2,3,␀,5`）、公式块收不进去（畸形公式多为转换器切坏了块，重转或人工核，**不要因为它把整本卡在闸门外**）。

修法见 §4 与 `tools/README.md`。

### 步 5：建库

```bash
stdq rebuild
```

秒级。会顺带：自动备份旧库到 `backups/`、按库重写 `catalog.md`、提示向量是否过期。

### 步 6：MD 与库逐条对账

```bash
python -m stdq.tools.verify_md_vs_db <新规范号>
```

退出码 0 = 完全一致。**只看条文总数不够**——总数对比能发现"掉了 10%"，发现不了**静默覆盖**：实测某本 25 条五段编号（`7.4.1.1.1` 型）被截成四段后**同号互相覆盖**，最后只留 1 条，总数几乎看不出异常，**24 条凭空消失**。

三类差异的定性：

| 差异 | 含义 | 处理 |
|---|---|---|
| 库中缺失（MD 有库无） | 几乎都是真漏抽 | 优先查 |
| 内容不一致 | 两边都有但文本不同 | 先看长度：库短 = 被截断；库长 = 可能把条文说明混进了正文（本该在 `note` 字段） |
| 库中多余（库有 MD 无） | 多半是历史手工补的条目 | 正常别删；但标了「疑条文说明被误当条文」的是垃圾，该清 |

脚本比对时已去掉全部空白（LaTeX 空格写法会漂移，逐字符比会被假差异淹没）。**不要**再叠加后处理——盘上的 MD 入库前已处理过，重复处理会改变解析结果。

与步 4 的分工：`detect` 只看 MD、用正则找可疑写法（能提前预警，但只认见过的花样）；本步是**结果导向的对账**，任何原因都能发现。**两个都要跑。**

### 步 7：跳号检查

```bash
python -m stdq.tools.stdq_check <新规范号>
```

**不要"必须修到 0"**——实测跳号里大部分是假警报，永远修不到 0。脚本会**自动分类**：

- 假·节标题 / 假·目录行 / 假·行内引用 → **忽略**
- `★真漏抽` → 必须补（修法见 §4）
- `？需查 PDF` → 走 PDF 定性（§4）

退出码 0 = 没有真漏抽。

### 步 8：截断条文修复（空行断句）

```bash
python -m stdq.tools.fix_truncated_clauses --dry-run    # 先看预览
python -m stdq.tools.fix_truncated_clauses              # 脚本默认就是写库模式
```

背景：MD 里条文被空行拆行时，入库遇空行断句，库里只存前半句。**共性 bug，新规范入库后必查。**

- ⚠️ **该脚本默认写库**（不是 dry-run），**没有 `--help`** → 要看用法就**读源码**，别执行
- 自带备份（`standards.db.bak.<时间戳>-fix-truncated`），出问题可回滚
- 改动性质是"库里存的是 MD 的前缀 → 补成完整文本"，改完**必须核对"有没有被改短"（应为 0）**
- ⚠️ **跑完必须复查"把下一条粘进来"**：脚本按"该条文号到下一个编号行"取全文，**若源 MD 本身把两条挤在一行**，它会把下一条正文一起写进上一条。用正则扫本轮被改的条文，命中就人工判
- **绕不过时手动改**：① 备份库文件 ② 从 MD 正则提取该条全文 ③ `UPDATE clauses SET content=? WHERE std_code=? AND clause_no=?` ④ **不要 rebuild**（会重排 id 使向量失效） ⑤ 有向量的用 `python -m stdq.tools.embed_patch` 定点刷新

### 步 9：废止关系核对

新版公告里如果写了"同时废止…"，`rebuild` 会用**标准句式**自动解析写入 `abolished` 表（整本废止的旧版会被搜索屏蔽、不编向量）。

```bash
stdq abolished <新版code>
# 或 SELECT * FROM abolished WHERE source_std LIKE '%<新code>%';
```

整本替换的场景应能看到 `source=新版, target=旧版, clause_nos=NULL, abolish_type='whole'`。

**抓不到就手动补**（公告没按标准句式写时会发生，方向是安全的——只是"该废而未废"）：

```sql
INSERT INTO abolished (source_std, target_std, target_name, clause_nos, abolish_type)
VALUES ('<新版>', '<旧版>', '<旧版全称>', NULL, 'whole');
```

### 步 10：专业主题标注

`rebuild` 会问主题（非交互环境下自动回退 `general`）。**别默认 general 了事**——主题影响检索时的主题加权：

```bash
stdq profession set <code> <theme>
```

13 个主题：`structure / plumbing / hvac / electrical / barrier_free / energy / gas / curtain_wall / fire / civil_defense / waterproof / roof / general`。

**建筑类型**则写进数据目录的 `type_map.json`（`examples/type_map.example.json` 是格式示例），依据是规范正文里的适用范围条款。这一步**不用改代码**。

### 步 11：章节目录

`rebuild` 会从 MD 的**目次段**抽章/节/附录写入 `clause_chapters` 表——**章节标题扩展词和章节命中加权全靠它**。

自查：

```bash
sqlite3 "$STDQ_DATA_DIR/standards.db" "SELECT COUNT(*) FROM clause_chapters WHERE std_code='<code>'"
```

为 0 说明 **MD 里没有可识别的目次段**（`## 目 次` 之类），此时检索会退化成"关键词 + BM25"，效果明显变差但不会报错。存量库要补：

```bash
python -m stdq.tools.backfill_chapters --validate     # 先看差多少
python -m stdq.tools.backfill_chapters                # 回填
```

### 步 12：生成向量

```bash
stdq embed-build
```

把库里每条条文编码成向量，供语义排序用。**耗时按机器差别很大**（强的几十分钟量级），跑之前先确认。

⚠️ **跑的时候 MD 与库只读**：不要同时 `rebuild`、不要改 MD——库和向量会对不齐，白跑一次。新发现的问题先记到文本文件，等它跑完再处理。

`rebuild` 之后向量会过期（库里条数变了），此时脚本会提示；重新 `embed-build` 才一致。

### 步 13：完成标准（逐项打勾，缺一不可）

- [ ] 粘连检测 0 命中
- [ ] OCR 字符体检 0 硬失败（MD 与库**两处**都扫）
- [ ] `rebuild` 通过
- [ ] 对账通过（MD vs 库逐条一致）
- [ ] 跳号检查无 `★真漏抽`（假跳号不算未完成）
- [ ] 主题标注完成（不是默认 general）
- [ ] 章节目录非空
- [ ] 向量已重建（若要用语义排序）

## 2. MD 格式契约

解析器只认这些形态。写 MD、造测试数据、判断"这本能不能入库"之前先看这节。

| 事项 | 约定 |
|---|---|
| **正文起点** | 依次找 `# N 总则` → 英文 `General Provisions` → `# 数字 ` 兜底。**没有章标题/总则的文件会从头扫**，封面、公告、目次都可能被当条文收 |
| **正文表格** | 必须写成 **HTML `<table>`**。Markdown 管道表基本不被支持（会被吞或散成文字）——转换器输出管道表时要先转 HTML |
| **条文说明的形态** | 说明区标记（`条文说明` / `起草说明` / `编制说明`，含页眉式变体）之后，条目要写成 **`3.1.1 说明正文`（条号 + 正文同一行）**；写成 `## 3.1.1 条说明`（条号后另加标题后缀）**抽不到** |
| ⚠️ **说明抽取有 120 行门槛** | 说明区标题只在**第 120 行之后**才找——**短于约 120 行的 MD 永远抽不到说明**，而且不报错、只是说明 0 条。造样例/测试数据必须把文件撑到 120 行以上，否则会把"门槛"误判成"解析器坏了" |
| **强条只认公告句式** | 「其中，第 X、Y 条为强制性条文」/「全部条文必须严格执行」。"必须/严禁"这类关键词只进"严格"标记，**不当强条依据** |
| **章节目录来源** | 目次段（`## 目 次` / `## 目 录`），缺失则章节能力失效（见步 11） |

## 3. 术语标准入库

适用：术语标准（"术语标准 / 词汇"命名的）。格式是"编号 + 术语 + 英文 + 定义"，与常规规范"编号 + 条文内容"完全不同——解析器按文件名自动切换提取逻辑。

**特例与坑**：

- 术语标准 PDF 多为扫描件，OCR 质量参差 → **转换后必查"OCR 丢点号"**：
  点号丢失会把 `2.1.1.14` 吞成 `21114`。检测：`grep -nP '^## \d{4,6}' 规范.md`，命中就按上下文相邻编号手工补点
- 术语表是**假名重灾区**（`の` → `、`），OCR 硬闸门必跑
- 术语标准基本无插图，转换器输出的孤立图片多为**误识别**（把术语行截成图）→ MD 里没有图片引用就**跳过图片步**，不建 images 目录
- 术语编号可能多达 4 段（`2.14.1.7`）→ 跳号检查脚本对 4 级编号**大量误报**，只信"MD 有、库无"的真缺：

  ```bash
  grep -oP '^## \d+\.\d+\.\d+(?:\.\d+)*' 规范.md | sort -u    # MD 编号（三段以上，排除节标题）
  # 与 SELECT clause_no FROM clauses WHERE std_code='X' 对比：
  # MD 有 DB 无 = 真缺；DB 有 MD 无 = 提取多余（节标题被误收）
  ```

## 4. 跳号检查与修复

### 4.1 分类怎么读

见步 7。**只有 `★真漏抽` 要动手**，其余忽略。

### 4.2 ★真漏抽的四种症状

| 症状 | 例子 | 修法 |
|---|---|---|
| 编号粘在上一行末尾 | `…的规定。9.9.18 空气调节水系统…` | 在编号前**断行**，再 rebuild / 并补条 |
| 标题行与第一条粘连 | `## 8.4.1附加空气渗透量…的测定8.4.1.1充分密封试件上的…` | 同上（注意：**行首已有编号时，解析器的"行内找编号"兜底不会运行**，所以这种必须断行） |
| 编号里的点被 OCR 成冒号 | `6.6:6地基基础设计等级为丙级…` | 改回 `.` |
| 条文号后跟数字正文 | `11.1.8250m及以上建筑物`、`4.6.135kV`、`11.9.9220V` | 编号与正文之间**补空格**（见 4.3） |

### 4.3 "条文号后跟数字正文"的检测与修复

粘连成 `11.1.8250m` 时，`rebuild` 会把它当成更长的编号吞掉，该条号没提出来。**粘连检测脚本抓不到这种**（它只查已知几类）。

- **检测**：找"行首编号后紧跟数字"的行——共性是条文以数字/单位开头（250m、220V、35kV）
- **修复**：在条号后补空格

  ```bash
  # 11.1.8250m及以上建筑物 → 11.1.8 250m及以上建筑物
  # pattern: ^(<缺的编号>)(?=[0-9])(.*)$  →  编号 + 空格 + 正文
  ```

  每个缺号先 `grep -n "<编号>" 规范.md` 确认它确实在 MD 里且被粘连，再补空格；修完 rebuild + 复查跳号检查
- 实测：一本五段编号的规范里，这类跳号一次出现 **20 余处**

### 4.4 拿不到结论时：回 PDF 定性

判"真丢条"还是"原文本来就跳"：

```python
# PDF 有文字层 → 全文宽松匹配（OCR 常在编号里插空格）
pat = re.compile(r'(?<!\d)' + r'\s*\.\s*'.join(re.escape(x) for x in no.split('.')) + r'(?!\d)')
# 命中 → 原文有 = 真丢条，从 PDF 补原文
# 未命中 → 原文本来就没有这个编号 = 不是丢条，记档忽略
```

PDF 是纯扫描件（无文字层）→ **按页渲染 + 视觉核对**：先看目次拿到目标节的**印刷页码**，从"正文首页 = 印刷页 1"反推偏移，只渲染目标页；小字看不清就放大裁剪。做视觉识别时的提示词要写明**"按原表逐行列出，不要按规律推测"**。

⚠️ **数字绝不外推**：OCR 漏行/截断时，**只展示能确认的部分**，并明说"库原文缺 N 行，需对照 PDF"。**禁止**按递增规律补数当依据——补出来的基本是错的（实测一张 12 行的表只留 4 个数，按"递增"补出的 11 行全错，原表是按视觉相邻分组的）。

### 4.5 库里"空壳条文"的 SQL 交叉验证

绕开检测脚本的兜底手段：查"正文很短但说明很长"的条目，多半是正文漏抽、说明被错位放进去了。

```sql
SELECT clause_no, length(content), length(note) FROM clauses
WHERE std_code='<code>' AND length(content) < 30 AND length(note) > 200
ORDER BY id;
```

## 5. 验证必须隔离（硬纪律）

在隔离目录跑建库/查询做验证时，**数据目录、socket 两个变量都要覆盖**：

```bash
export STDQ_DATA_DIR=/tmp/x/data                        # 库与 MD
export STDQ_SOCK=$STDQ_DATA_DIR/stdq_daemon.sock        # 默认跟着数据目录走
```

**只设数据目录不够**：如果系统里还有一个常驻进程在跑（监听它自己的 socket），查询会走它、拿到**别的库**的结果——你以为在验证新库，其实看的是旧库，结论完全是假的。

改引擎代码或造样例后，一律按上面隔离，**再补一次"全新目录 → 只照 README 步骤跑"的端到端验证**。

## 6. 附录条目

附录（`附录 A` / `A.1` 这类）与正文分节，抽取路径不同。入库后自查：

```bash
stdq appendix <code>
python -m stdq.tools.apx_crosscheck          # 附录抽取稳定性交叉验证
```

若附录缺失或不全：先确认 MD 里附录区的起止能被识别（`本规范用词说明` / `引用标准名录` 这类尾部标记会终止识别）；再按需补库：

```bash
python -m stdq.tools.splice_appendix <code> <新附录MD> [--apply]   # 把缺的附录拼回主 MD（默认 dry-run）
python -m stdq.tools.backfill_appendix <code>                       # 定点补库，不动现有条文
python -m stdq.tools.backfill_apx_sections <code>                   # 补附录的节级目录
```
